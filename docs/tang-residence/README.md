# 唐宅场景档案

更新时间：2026-10-18。档案版本：`0.1`（初始工作设定，场景开发待实施）。初始设计提交：`750a5e3`。

本目录持续维护“这个宅子在什么时代、什么地方、由什么人怎样使用，以及这些条件如何决定每项呈现”。它是唐宅开发、补证、素材制作和后续调整的共同参考。当前档案登记的是设计，不是已实现的场景清单；用户要求建立维护体系，不等于逐项确认了初始方案中的暂定值。

## 2. 权威顺序与避免冲突

1. 用户最新明确指令决定目标和授权范围；把指令落实到受影响记录，不依赖聊天记忆。
2. 当前主数据由上表指定文档维护。技术方案、平面图、代码、配置、截图和说明应引用它们，不各自保留一套可独立修改的设定。
3. 史料决定某项历史主张能否成立，创作设定决定本宅选用什么；两者冲突时记录问题并修正设计，不能把偏好的画面标成史实。新史料不能静默改掉用户设定。
4. 遇到文档、代码或图面不一致，记录差异与影响，明确当前值和待修内容；不以“代码已经这样”倒推设计已通过验收。历史记录和旧提交保留。

## 3. 关联方法

`SET（场景设定） → SP（空间） → EL / OT（构件 / 物品类型） → PL（布置）`，并分别关联 `H（历史依据）`、`AS（素材）`、`CR（变更）` 与 `Q（待办）`。

- 类型与布置分开：同一种碗可共享模型，但在书斋、厨房的用途、数量和磨损分别登记；同一模型不意味着所有实例都能任意复制。
- 原型与本宅物品分开：馆藏存在一面镜子，不表示本宅已经决定拥有它；年代相近、史料等级高也不自动通过本宅适用性复核。
- ID 一经使用不得改作另一对象。删除或替换时标记停用/被替代，保留原关系和原因。显示名称与文件路径变化不改变对象身份。
- 未来代码节点/实例组、配置项和发布素材与档案 ID 建立映射；当前未开发处统一写“未建立”，不能虚构存在的代码路径。
- 普通重复构件允许按可追踪实例组登记：写明生成范围、数量规则与成员获取方式。重点器物与独立交互物必须能定位具体实例。

## 4. 状态分开记录

| 维度 | 使用状态 | 不能混为一谈 |
| --- | --- | --- |
| 设定 | 工作设定 / 待定 / 已调整 / 已停用，附决策出处 | 工作设定不是用户逐项确认，也不是史实 |
| 历史判断 | 待补证 / 有限采用 / 已复核 / 不采用 | A/B/C 是依据类型，不是实现或许可状态 |
| 实现 | 计划 / 制作中 / 已接入 / 已验证 / 已停用 | 有文档、模型或截图不等于全部验收完成 |
| 素材许可 | 原创待归档 / 已核实（限明确范围）/ 未核实 / 不采用 | CC0 不证明年代，馆藏图片开放不覆盖其三维扫描 |
| 变更 | 待处理 / 处理中 / 已完成 / 已替代 | 未关闭的受影响记录不能随上游任务自动完成 |

当前 3D 构件、家具、器物、布置和交互均处于“计划”；实际素材路径、摘要、代码映射和场景验收记录尚未建立。本轮只有方案平面图等文档资产已存在。

## 5. 每次任务的最小维护动作

开始前读取设定与变更记录，定位受影响的稳定 ID；新增设计先登记依据和依赖。实施时同步更新当前记录与问题，完成前按[变更流程](change-control.md)复查全部影响项，更新方案/索引/CHANGELOG，并按项目要求仅提交相关文件、推送当前分支。

不要求每次抄写整套档案。无影响的领域明确记“无需调整及原因”；未知值明确留待办。发现新对象未登记、来源不明、关联失效或背景变更未复查时，不能把相关场景范围标为已验证。
