# 游戏文案规范

创建及更新：2026-10-22。适用于当前住宅与海角灯站。剧情事实以[三天代班设计](technical-plans/2026-10-21-lighthouse-three-day-story.md)及已交付章节为准，工程实现和本次验收见[文案方案](technical-plans/2026-10-22-game-copy-and-voice.md)。后续新增任务、设备提示和故事页先按本文写，再核对当前实现。

## 先确定谁在说话

| 声音 | 对谁说、想做什么 | 句子习惯 | 示例 |
| --- | --- | --- | --- |
| 周师傅 | 向临时代班的人交代熟悉的地方 | 用常用词、具体动作和顺口的叮嘱；不夸赞玩家，不预言未来 | “擦完别急着走，再看一遍。” |
| 岸站值班 | 与岛上同事确认工作、说明航务 | 先说结果/安排，再交代原因；关心落在能解决的事上 | “外海浪还没退，今天的艇过不去了。你先留站，接送有消息我再通知。” |
| 玩家工作记录 | 给自己和下一班留可用的记录 | 写当时看见、做完和还没查明的事；不用验收报告腔 | “面板已擦净，回头检查过，读数也重新对照了。” |
| 玩家个人记录 | 给自己留一句话，也可以不写 | 不替玩家规定情绪、人生经历或与他人的关系 | “现在不用看地图了。”原句保留 |
| 操作界面 | 帮玩家找到下一步并理解限制 | 地点＋动作＋必要条件；短确认；错误给恢复办法 | “回首层读表，再上灯室看灯。” |
| 仪表/设备 | 报当前状态 | 术语准确、信息短；故障与未知分开 | “主灯停机，备用灯接替中。” |

安静和克制来自具体的事情。不要在每封信结尾升华孤独、责任、守望、光或归属；不用“岛在等你”“每一束光都有故事”等句子替人物说感受。生活细节只取自已有场景和设定，不凭润色添加茶叶、家属、旧事故、私人约定或人物去向。

## 事实与感受

- 玩家受过训练，只是初到灯站；不写成什么也不懂的新手。姓名、性别和过去留白。
- 周师傅已先离岛短休。他的便条可亲切，不暗示失踪或遇险。
- 原定满三天后的中午接送，下一班随艇来。准备好报告不代表已交班，钥匙仍在玩家手里；晚做任务使用实际日序。
- 接送受外海涌浪影响。岛边雨停、天晴不代表船能靠工作码头；码头位于本章可玩范围之外。
- 旧呼号只是一条显示标签。原呼叫与时间保留；岸站无发送记录不等于证实了任何超自然身份。
- “没看到污膜”“怀疑有污膜”“已确认污膜”“已擦净并复查”是不同结果。已完成的工作不因为文案更有气氛就变成故障或遗憾。
- 日间待机不用解释为“无强制导航需求”。夜间或雾中主灯/备用/无灯必须如实呈现。

## 界面怎么写

先给玩家能用的信息。按钮用动作和对象，如“记下读数”“擦拭面板”“重试保存”。附近说明写条件，别把长句塞进按钮。必要的普通大灯检查3秒、维修试机30秒/一圈、备用灯10秒白闪、2秒巡视/5秒细查、白天停灯和雨量限制要保留。

首次说明可详细，重复反馈简短。“读数记下了”已经够用。当前读数失效时说“设备状态变了，请重新读表”，不要让玩家理解内部修订号。暂停说明说“阅读时暂停”；等待时说“灯站照常运行，低电或出现问题会停下”，同时明确时间确实会过去，检查仍需亲自做。

| 常见原句 | 根据语境改写 |
| --- | --- |
| 无强制导航需求 · 日间待机 | 白天，灯处于待机状态。 |
| 本次做过的工作 | 已办的事 |
| 没有已确认的关键待办 | 目前没查出需要接着处理的问题。 |
| 三项现场证据需属于当前日序与有效修订 | 今天的读数、灯和保护面都查过，才能发报告。设备有变化时要重查。 |
| 输入处置及独立复查 | 清洁面板，再检查一遍，回首层对照读数。 |
| 已接受时间/结算场景小时 | 已经过了…小时（岛上时间） |
| 当前会话保持 | 你可以接着玩。 |

这些是语境示例，不做全局词语替换。“输入”在仪表读数、“复查”在工作记录中有用；不能为了口语化丢掉含义。记录里的数值与单位保留，先写哪项读数，再写比较条件。存储错误明确“这次没存上”“旧档还在”“可以重试”，不能在没有验证时保证数据必然完好。

## 后续编辑流程

1. 列出这页的说话者、地点、当前任务、已知事实和可执行操作。
2. 写一遍人会怎么说，读出声，删掉重复的解释和模板收尾；已自然的句子保留。
3. 对照功能检查时间、数量、否定、条件、完成状态和来源，尤其是待查、清洁后复查、交接未完成、存档失败。
4. 看实际界面：手机上是否能读完，按钮是否截断，关键提示是否藏在长文后，键盘和辅助标签是否一致。
5. 修改持久文本前检查存档校验、事件分派和原文回看。稳定ID/判定字段不当作文案随手替换；新增内容遵循同样的数据与展示分离方式。

本规范应用[Humanizer-zh](https://github.com/op7418/Humanizer-zh)的中文编辑方法和[UX Writing](https://github.com/content-designer/ux-writing-skill)的界面与口吻框架；版本、许可和适用边界见方案。技能提供复核方法，人物可信与否仍须回到本项目的场景和事实检查。不要用AI检测分数或自行打分代替页面审阅。
