## 背景与目标

现有灯塔可以到达、登高和开工作灯，但导航灯没有运行状态，维护记录也不会变化。本项目先交付一个能反复体验的基础循环：**读面板、登塔观察、处理一处污损、复查记录、确认夜间自动运行**。玩家完成检查后能看到设备和记录发生对应变化，原住宅游览仍可自由进行。

首版保持晴朗、稳定供电、设备无随机故障。完整备用灯、充放电和机房属于子项目二；首版设备说明标明该能力尚未加入，面板不显示虚构的“备用正常”或持续100%的电量。

| 必须交付 | 后续承接 |
| --- | --- |

| 单束白色旋转信号，同一方向10秒一闪，6转每分钟 | 子项目二的驱动故障及备用灯 |

| 三项确定性巡检，其中一项含可观察的清洁动作 | 子项目二的更多设备、诊断和工具 |
| 会话内逐日清单、观察与操作记录 | 子项目二的本地保存与继续值守 |

本项目完成时，玩家从住宅出发，亲自操作灯塔并返回，能够说清“什么时候亮、怎样确认在工作、清洁改变了什么、记录在哪里”。天气和故障即使尚未开发，这个版本也能独立使用。

## 首次体验及每日循环

首次仍在默认12点进入，不自动开启时间流转。首次访问首层面板时，用简短说明给出本轮三项巡检和顶层位置，玩家可随时离开。路线沿用现有住宅、步道、五层垂直梯和外廊。

| 项目与标识 | 玩家操作 | 真实完成依据 | 反馈与重复行为 |
| --- | --- | --- | --- |
| 运行模式检查 `check-control` | 近距离打开首层面板，读取模式和实际灯态，确认本次读数 | 读取成功后形成有时刻的观察记录；不能隔墙触发 | 显示“自动／日间待机”或“自动／导航运行”；重复查看更新时间，不重复奖励 |
| 灯具与转台检查 `check-optic` | 到顶层看灯具；白天从灯座附近的入口启动试灯，关闭界面后观察一整圈 | 连续有效观察10个活跃秒，转台完成一圈且出现对应出光；不要求每帧都处于白闪峰值，暂停不累计 | 指示观察进度，失去有效视线则重新累计连续观察；完成后记录“本次周期观察正常”，不冒充全面检修 |
| 光学保护面检查 `check-cover` | 检查指定可达表面，首次有固定轻度盐膜，按需擦拭后复查 | 先获得观察结果，再完成清洁动作，最后复查表面已洁净；没有污损时检查即可 | 污损外观、出光修正和记录同步变化；清洁不会给转台或供电加“耐久度” |

三项完成后，记录夹显示本轮检查摘要。18点灯塔会自行启动，玩家可以从住宅或途中看到灯头信号，再到面板查看客观运行事件；起灯不以清单完成为前提。初始盐膜是固定教学内容，清掉后保留；次日只需检查仍然洁净，不每日重刷同一污迹。

新一天的三项检查按总方案的连续自动跨午夜事件重新建立，设备真实状态保留。没有惩罚、货币、等级和固定每日维修指标。记录只在本次会话保留，刷新重建教学初始状态；跨会话继续由子项目二实现。

## 基础运行与操作规则

### 自动和试灯

候选状态为 `day-standby`、`night-running`、`test-running`。首版只开放自动和短时试灯；检修模式留给具备备用能力的子项目二。

- 日程按 `[18,24)` 与 `[0,6)` 运行；18点开启、6点待机。日程是场景示意规则，现实依据保留在总方案。
- 白天试灯最长30个活跃秒，可主动结束；夜间试灯不会关闭导航或重新计算起灯事件。顶层入口避免玩家从首层启动后在爬梯途中耗尽测试时间。
- 昼夜切换优先保障正常导航：测试期间跨18点直接转夜间运行；跨6点仍有有效测试时可继续到测试结束。
- 清洁仅允许白天自动待机、转台停止时进行。晚间或试灯中说明当前不能擦拭；本版不给玩家任意关闭夜间主灯的开关。
- 清洁目标为主灯非旋转保护罩上可从原楼面安全触达的表面，先核对距离和碰撞；不要求踩上灯座、越过护栏或伸出外廊。
- 清洁采用点击后1.5个活跃秒的短动作，保持近距离与无遮挡；走开、转入爬梯、开界面或失焦中断，不扣耗材，完成后一次性更新表面和记录。确认后复查才完成该检查。
- 动作执行和提交均复核停机条件；跨18点自动起灯或启动试灯时立即中断清洁，保留原污损和未完成记录，不能在运行状态下补交清洁结果。

30秒、10秒观察和1.5秒清洁均是交互初值，实施时以可操作性调整并留档；它们不代表真实检修规程。

### 灯头表现

拆出可旋转的光学头及不对称单束出光面，塔架、灯座、外层玻璃保持静止。当前[灯塔细节](../../src/examples/LighthouseDetails.ts)按材质合批，必须先把旋转部件从共享批次中分离，不能连首层面板或整座保护框一起旋转。保留现有中心碰撞和通路。

远处的亮闪依据观察方向与旋转光束的夹角求值，近处能看出转台和光源；不把整个灯头每10秒统一熄灭当作旋转效果。首版不做长距离海面或住宅扫光、体积光柱及新增阴影图。出光强度仅受本地污损修正，用游戏参数表达轻度变化，不声称实际射程已经标定。

## 数据与现有代码接入

以下新模块名称为计划职责，尚未创建；允许实施时调整文件划分，不改变本项目边界。

| 位置 | 计划职责 |
| --- | --- |
| `LighthouseOperation.ts` | 纯逻辑运行状态、日程、测试剩余时间、转台相位与客观事件 |
| `LighthouseInspection.ts` | 三项检查、表面状态、观察证据、清洁事务、按日清单 |
| `LighthouseBeacon.ts` | 光学头及方向相关出光，读取逻辑状态，不自行判定时间 |
| `LighthousePanel.ts` | 面板、任务和日志的中文可读界面，处理命令与反馈 |
| [Room.ts](../../src/examples/Room.ts) | 统一推进、交互注册、暂停与资源所有权；不把全部逻辑堆在场景类中 |
| [RoomInteractions.ts](../../src/examples/RoomInteractions.ts)、[RoomItemInspection.ts](../../src/examples/RoomItemInspection.ts) | 沿用距离、遮挡和查看返回；新增设备动作需明确接口，不把旋转设备克隆成静态纸张 |
| [LighthouseRecords.ts](../../src/examples/LighthouseRecords.ts) | 保留记录夹入口和原图集，动态内容通过可读界面呈现，移除永久“日间待机”造成的误导 |

面板和日志复用既有对话框式暂停及指针锁定恢复机制，增加专用暂停原因时更新共享类型，不借用会被其他界面提前解除的原因。设备观察在关闭界面后的实际场景中计时，避免“打开详情暂停设备，任务又要求在详情里转一圈”的冲突。保留E抓梯优先与已有鼠标交互，不再给整塔新增全局抢占按键。

日志至少含事件编号、值守日、时刻、对象、操作或观察、结果及来源。运行、观察、处置分开记录，重复点击不重复写入同一结果事件。环形保留最近7个值守日的摘要，清单与真实表面状态不因日志裁剪而丢失。稳定设备标识在总方案集中维护。

时间、暂停、手动选点和证据失效规则服从总方案的共用约定。首次刷新仍为12点；在住宅时导航状态继续运行，不能使用原工作灯的“靠近相机才有效”门控。

## 验收方法与资源目标

逻辑用例重点覆盖17:59至18:00、05:59至06:00、测试与日程重叠、清洁中跨夜或启动试灯被正确中断、不同帧步长的10秒周期、取消动作不产生清洁结果、检查证据与对象状态一致、重复命令幂等及按日清单。禁止用每帧回调次数代替时间。

浏览器独立托管最终生产目录，真实从住宅到五层顶层，完成三项检查、取消与复查，再回住宅看夜间运行。近景检查仅用于补充，不能代替真实路线上下梯。验证隔墙无操作、爬梯和地图恢复、原工作灯、住宅门灯帘/镜面、小电驴和Inspector；至少检查可用Chrome及跨引擎横竖屏/DPR，限制平台分别记录。

按[资源原则](../resource-optimization-principles.md)完成相关测试、类型检查、开发及生产构建、发布校验、全部分包与说明文件的根/子路径访问和摘要、实际首屏JS测量。四项硬预算为两个目标GLB≤4.25MiB、运行素材≤16MiB、实际首屏JS≤3MiB、完整发布目录≤41MiB；包含必需异步JS。

首选原创程序几何、既有材质和音效，无新增下载、依赖、相机、RTT或阴影图；新增几何设计目标≤8,000顶点、≤12网格、≤3材质，主灯最多增加1盏局部无阴影光源。它们是设计上限，不是实测成本；若能仅用方向相关发光实现目标，应记录实际选择。保持pure或精确导入与显式注册，源资产与旋转部件变化可回溯。
