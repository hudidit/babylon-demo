## 1. 结论与交付边界

先把户型数据变成三维场景的唯一布局依据，完成全屋可通行的基础结构；随后重排客厅和小书房，再依次完成主卧套间、次卧、厨房/公卫、阳台。每一阶段都交付可检查的场景、测试、资源记录与独立Git提交，不同时重做全部房间。

首次方案交付仅编写文档。阶段A完成纯户型数据/转换、稳定门ID、归属/生命周期和共享材质，先接入旧双房。2026-10-17继续完成B～F：运行入口已切换到八房新屋，七间室内房间已布置；阳台保持基础结构，G待实施。

## 2. 立项时现状与改造原因（`ab3368c`）

- [HouseFloorPlan.ts](../../src/examples/HouseFloorPlan.ts)已经定义八个房间的米制矩形和门连接，但它同时包含SVG绘制；实际场景没有消费这些布局数据。
- [Room.ts](../../src/examples/Room.ts)仍直接创建40×40单位书房，写死家具导入坐标、第一人称出生点和七组镜头。[RoomLivingRoom.ts](../../src/examples/RoomLivingRoom.ts)仍创建X=20～54、Z=±20的旧客厅，并把步行限制在旧双房的大矩形中。
- [RoomLayout.ts](../../src/examples/RoomLayout.ts)只有旧连通门、客厅和共享墙区段。新图中的书房在北侧，旧场景书房在客厅西侧；仅调整边界数值不能完成迁移。
- [RoomFurnishings.ts](../../src/examples/RoomFurnishings.ts)把通用家具工具、书房装修、家具摆放和材质初始化混在一起；`section()`还将房间归属固定为`living`。静态几何会合并并冻结世界矩阵，不能在最终合并之后简单挪动或缩放父节点。
- [RoomLighting.ts](../../src/examples/RoomLighting.ts)依赖“客厅/非客厅”和特殊`shared`判断；新增卧室会被错误归入书房。光源坐标、范围与阴影刷新也需要按房间配置。
- [RoomInteractions.ts](../../src/examples/RoomInteractions.ts)的门运动覆盖`root.rotation.y`，扫掠检查假定门扇初始沿世界+Z，并使用旧玩家半径。新户型同时有横、纵向门，直接旋转旧门根节点会导致开门方向或扫掠保护错误。
- [RoomFloorPlan.ts](../../src/examples/RoomFloorPlan.ts)目前用旧世界X=20区分所在房间；新场景上线后必须改用统一坐标和房间边界查询。

最重要的内容变化是书房64m²→10.2m²。旧书房包含书桌、三把桌椅、会客沙发、扶手椅、窗边桌、书架和古董柜；必须分配到合适房间，不能把所有物品一起缩成原来的尺寸比例。

## 3. 冻结户型与坐标约定

沿用已确认的布局，不通过改变房间尺寸解决摆放冲突：

| 房间ID | 地图左上角（m） | 宽×深（m） | 连接 |
| --- | --- | --- | --- |
| `master` | (0, 0) | 5.4×4.8 | 客厅、独享主卫 |
| `study` | (5.4, 0) | 3.0×3.4 | 客厅 |
| `kitchen` | (8.4, 0) | 2.4×3.4 | 客厅 |
| `ensuite` | (0, 4.8) | 2.4×2.4 | 仅主卧 |
| `bathroom` | (2.4, 4.8) | 3.0×2.4 | 客厅，位于主卧外 |
| `bedroom` | (0, 7.2) | 5.4×3.6 | 客厅 |
| `living` | (5.4, 3.4) | 5.4×7.4 | 入户及各公共入口 |
| `balcony` | (5.4, 10.8) | 5.4×1.5 | 客厅 |

推荐继续使用5场景单位=1米，统一地面Y=-5，地图北侧对应世界-Z。将室内范围中心(5.4, 5.4)m映射到世界XZ原点：

```text
worldX = (planX - 5.4) × 5
worldZ = (planY - 5.4) × 5
planX = worldX ÷ 5 + 5.4
planY = worldZ ÷ 5 + 5.4
```

由此室内范围为X/Z=±27，阳台向南延至Z=34.5。房间内家具使用以该房间左上角为起点的米制局部坐标；只在统一转换层转成引擎单位，不在各模块重复换算，也不通过房间根节点缩放家具。

户型标注未扣墙厚，实施时将矩形边界定义为墙中心线。首期墙厚暂定0.10m、室内净高2.8m；内侧可用边界扣除半墙厚，门宽、门框侵占和实际通行净宽分别计算。家具以可用边界摆放。地图面积继续按现有规划口径显示，不把它改称净使用面积。第一人称眼高暂定地面上1.6m（Y=3），碰撞体、门扫掠半径和出生位置共同校准；移动速度倍率偏好与现有操作方式保留。

## 4. 代码结构与数据职责

以下新增文件名为建议，实施时可按实际规模合并，避免建立复杂框架：

| 文件/模块 | 计划职责 |
| --- | --- |
| 新增`HouseLayout.ts` | 纯数据与纯函数：八房矩形、稳定门ID、连接/轴向/开向、统一尺度和双向坐标转换、点所属房间、内侧边界 |
| 调整`HouseFloorPlan.ts` | 只负责从统一布局绘制SVG；迁移期可重导出旧数据名称，最终消除两套布局定义 |
| 新增`HouseArchitecture.ts` | 地面、墙段、真实门窗洞、天花、基础线脚、阳台安全围栏，以及环绕剖面显示 |
| 新增`HouseRooms.ts` | 小型房间注册表：根节点、内容构建函数、状态、家具/灯具/交互归属、资源与销毁；不是另一套引擎或ECS |
| 新增`HouseWalking.ts` | 从已生成结构取得边界/安全出生点/当前房间，统一第一人称高度与碰撞参数 |
| 调整`RoomFurnishings.ts` | 通用家具builder与共享材质；按房间/材质/剖面层合并，取消隐式`living`归属 |
| 拆分房间内容模块 | 书房、客厅分别重排；两卧共享床/柜基础组件，双卫共享洁具组件，厨房和阳台独立配置 |
| 调整`RoomLighting.ts` | 房间光源描述、共享环境光、墙/门双侧归属、局部阴影失效与灯具状态 |
| 调整`RoomInteractions.ts` | 通用门安装姿态与局部运动、扫掠保护参数、房间级注销；复用现有抽屉/灯/物品查看逻辑 |
| 调整`Room.ts`与`RoomFloorPlan.ts` | 场景编排、单套相机与模态输入协调；镜头锚点和地图定位读取同一房间注册表 |

房间定义保持静态，运行状态另存为`planned / shell / furnishing / ready / error`。`shell`表示地面/边界/开口已可检查，不表示家具已完成；`ready`只能在该房间内容、资源和交互验收通过后设置。替换当前`hasContent`的单一布尔语义，地图显示“规划 / 基础结构 / 已布置 / 加载失败”，失败时保留可用结构及其他房间。

每个房间返回显式的静态网格、动态交互、灯具、镜头锚点与清理句柄。一个Scene、一个Engine，保留环绕/第一人称/物品查看三种相机角色，不按房间创建引擎。共享纹理和材质由场景持有；房间释放不得销毁其他房间仍在使用的资源。异步导入检查房间构建代次及场景是否销毁，避免过期结果再次挂入场景或重复注册动作。

## 5. 全屋结构、门和通行

### 5.1 墙体与剖面

1. 从房间边界提取水平/垂直线段，在共线端点和T形交汇处切段；公共边只生成一份物理墙，保存相邻房间ID。
2. 根据门数据切出开口和上方过梁；护墙、踢脚线、门框同时避开开口。窗口在房间外墙配置，不能继续沿用旧书房西窗和客厅北窗的世界坐标。窗口配置记录所属房间、墙面、沿墙偏移、宽高和窗台高度；B阶段同时放置家具占位，先协调可用安装墙面再开洞。公卫是内部房间，不在与卧室相邻的墙上伪造外窗，后续用排风外观和照明处理。
3. 客厅是包含入户/餐区的完整矩形，内部不生成旧过廊隔墙。主卫没有通公卫或客厅的门，公卫没有穿过主卧的入口。
4. 环绕模式移除天花遮挡，并对前景墙做剖面显示；第一人称恢复完整壳体。渲染显隐和物理碰撞分开管理，隐藏展示墙不能留下隐形挡门，也不能让玩家穿墙。
5. 阳台在基础结构阶段就有地面、边界与围栏碰撞，内容虽未布置也不能跌出房屋。

### 5.2 门的通用化

- 为每个开口分配稳定ID；书房/客厅门可保留已有`connecting-door`交互ID，迁移其位置与方向，其他门使用独立ID。
- 使用“安装节点（固定位置/朝向）→运动节点（局部旋转）→门扇/把手”的层级。运动更新不覆盖安装朝向；扫掠检测把玩家位置转换到安装节点局部空间，再按玩家碰撞半径检查整个角度步长。
- 普通单扇门复用平滑开合、中途反向、玩家受阻暂停、动态碰撞/阴影和原音效。阳台推拉门使用平移与独立扫掠范围，不能套用单扇旋转算法；基本开口在结构阶段保留，推拉门完成于阳台阶段。
- 门扇和抽屉不进入静态家具合并；动态矩阵、碰撞和声音取实际世界位置。门两侧都能拾取，同一个门只注册一次。
- 第一人称默认从客厅入户区的安全位置开始，避开门扇扫掠区。入户门打开后面向客厅，本方案暂不开放室外街景与室外行走；外侧边界需可理解且不能走入无地面的区域。
- 原矩形`constrainWalkingPosition()`不能作为新屋完整碰撞。使用全屋地面范围和真实分隔墙/门/家具碰撞，末端边界保护只负责防止越界，不把位置强行夹到不属于任何房间的凹角区域。

按照真实占地重排，优先保留已有风格、资产品质和交互。移除旧坐标布置而不降低家具整体比例；程序家具按合理尺寸重新参数化，GLB按实际包围盒放置并保留其坐标系转换。

| 现有内容 | 首轮迁移安排 |
| --- | --- |
| 书桌、两抽屉、桌椅、台灯和信件 | 北侧小书房核心；减少多余桌椅，保留两抽屉、灯和信件原ID/行为 |
| 木书架及书本 | 书房靠墙，先实测柜深/椅子拉出范围，确保进门和靠近桌面可行 |
| 窗边桌三抽屉 | 改作客厅收纳/玄关边柜，放在不会侵入入户及卧室门扫掠的墙段；更新提示名称 |
| 古董柜三抽屉 | 先放客厅合适位置，保留抽屉结构与品质；不等主卧完成后才恢复已有三抽屉 |
| 阅读沙发、扶手椅、落地灯 | 纳入客厅会客/阅读布局；重复座位是否保留由占地检查决定，不能塞回小书房 |
| 客厅主沙发、茶几、壁炉、陈列柜和台灯 | 在5.4×7.4m内重新布置，给入户/餐区及西侧三处门留连续通路 |
| 窗景、窗帘、挂画、植物与材质 | 按新的外墙面和家具锚点复用；窗景复用不等于生成新的室外环境 |

优先在客厅/书房迁移阶段恢复八抽屉、三盏灯、信件与书房门的既有能力。若实际尺寸验证证明某件家具必须换位或删减，先在该阶段方案记录具体物品和理由，不把画面内容减少称为无损优化；不以改大书房来容纳旧摆法。

合并/冻结在最终房间变换和家具位置确定后执行；维持按房间、材质及剖面层的合并批次和静态碰撞分区。动态交互保留独立节点。原桌面细节、藏书角、阅读区镜头改用物件锚点生成，位置随家具移动；阅读区和古董柜迁到客厅后，镜头/地图房间归属也随之更新。

## 7. 灯光、地图、音效与加载

- 全屋共享HDR与环境补光，各房按窗口/主要灯具定义局部光。`ownerRooms`等明确归属覆盖普通网格、共享墙和门，取消“非客厅就是书房”的判断。
- 不给每件装饰灯都建立阴影图，也不机械复制八套旧书房照明。保留必要的主要受光与接触阴影，按房间大小/近景覆盖选阴影尺寸；静态缓存继续保留。开门、抽屉移动和灯开关只使受影响房间及共享边阴影失效。
- 仍复用现有SSAO、抗锯齿、曝光和物品查看后期。房间新增后必须复核穿墙漏光、开门两侧亮度和镜面/玻璃排序，不通过直接关闭已有后期满足预算。
- 新场景采用同一布局版本后，地图按世界→米制坐标显示实际房间、位置和朝向。旧坐标阈值删除；精确点在布局版本不一致或位置无效时隐藏，不能继续伪精确定位。当前房间高亮与定位点同时读取同一转换函数。
- 未布置房间保持`基础结构`状态；地图不标为已完成。初期不增加地图传送，房间预设只改变环绕观察位置；第一人称切换和查看地图/信件继续保留原姿态及指针锁定恢复。
- 原音效缓冲与设置继续共享，新增同材质门/抽屉/开关复用已交付声音。新位置由实际网格世界矩阵提供，房间迁移后检查空间声道和距离衰减；不新增脚步、音乐、流体或复杂声学系统。
- 首期全屋基础结构直接生成，新增房间优先程序几何和共享素材。结构生成不等待全部模型；关键导入失败时提示具体房间并允许重试，不能让整个场景永久停在加载状态。确需内容懒加载时才增加状态机/分包，并把分包、首屏预热和完整交付分别统计。

## 8. 分阶段实施与验收出口

阶段按A→B→C→D→E→F→G推进。C可分“客厅”“书房”两个小任务，D/F也可按房间各自提交；基础数据/通行/注册稳定之前不同时装修多间房。阶段A先保持旧双房可用，B有意交付可漫游的全屋基础结构，C再恢复装修；这段过渡必须明确显示为基础结构，不冒充原画面已经迁移完成。旧完整场景通过Git历史回滚，不长期把两套房屋和引擎同时放入运行页面。
