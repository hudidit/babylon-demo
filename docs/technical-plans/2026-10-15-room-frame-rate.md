## 背景与现状

用户反馈 30 FPS 下移动和旋转不流畅。`RoomScene` 显式设置 `engine.maxFPS = 30`，此前各轮约 30 FPS 的采样受到应用限帧影响，不能证明场景达到硬件性能上限，也不能作为 60 FPS 的发布验收依据。

浏览器当前在 1791 × 1228 视口、WebGL2 / Apple M6 上显示约 30 FPS；Inspector 的 GPU 时间约 25～27 ms，需在关闭 Inspector 后复测，判断是否还存在 GPU 瓶颈。静态阴影已缓存，原生 CSS 像素渲染、SSAO2、FXAA、辉光和锐化均开启。

开始排查时，工作区另有资源体积方案和阶段 A 基线采集的未提交工作，随后由该任务独立提交为 `7897bd9`。本任务保留其原始记录，仅同步专项方案后续实施的 60 FPS 验收目标；不改资源、配置或阶段 A 基线。

## 目标与范围

- 移除 30 FPS 应用上限，按浏览器刷新节奏渲染，允许 60 Hz 及更高刷新率。
- 以稳定 60 FPS（60 Hz 下每帧约 16.67 ms）作为交互性能目标，覆盖六个视角、环绕旋转和第一人称移动。
- 固定分辨率、设备、生产构建和采样方式，分别记录实际帧间隔、CPU 场景提交时间及可用时的 GPU 时间；不以 CPU 时间推算实际 FPS。
- 优先保持画面；若解除限帧后仍超预算，再按测得的 GPU 开销优化重复渲染或后期，不直接通过全局降低清晰度掩盖问题。
- 不承诺所有设备均达 60 FPS；明确实测设备、分辨率、稳态与首次加载的边界。

## 方案及取舍

1. 删除 `maxFPS = 30`，保留引擎默认不设应用上限的行为。无需改成固定 60，避免限制高刷显示器。保留页面隐藏暂停和原分辨率策略。
2. 建立临时浏览器测量面板，在真实 Chrome 中对照限帧前后；最终源码移除临时采样入口，保留测量方法与结果。
3. 在同机默认视口和 1280 × 720 / 1920 × 1080 下采样。预热后统计 FPS、帧间隔中位数/P95、超时帧比例及 CPU/GPU 时间，额外覆盖持续相机运动。
4. 如需优化 AO 或阴影采样，先做开关对照定位成本，再比较全景、家具接触和近景画面，记录参数及取舍。避免无依据地改模型、光照或材质。
5. 修正现行方案中的 30 FPS 目标；历史数据保留并标注限帧条件。更新索引、变更日志，与代码和性能记录一同提交推送。

### 排查中新增的范围

解除限帧后，1791 × 1173 默认视口的六个静止视角约 59～60 FPS，但持续第一人称移动约 35 FPS。`Scene.onBeforeRenderObservable` 在相机更新之后触发，原 CPU 提交采样漏掉了相机输入和碰撞计算，需要补充引擎整帧 CPU 时间。

自建家具按材质合并后，一个渲染子网格可能横跨整个房间。移动时对其进行逐三角形碰撞检测，无法利用原先每个零件的局部包围盒。拟保留原合并渲染及精确碰撞几何，为碰撞单独保留原零件的索引范围和包围盒，通过 Babylon 的 `getCollidingSubMeshCandidates` 公共回调提供候选子网格。碰撞分区不加入渲染子网格，避免增加绘制批次；静态矩阵冻结后更新分区包围盒。先通过碰撞开关对照确认收益，再实施并验证碰撞结果等价。

初步高分辨率近景的渲染回调频率出现约 50 次/秒的波动；检查发现多个书房窗口同时渲染，而且浏览器视口覆盖最初作用于另一个测试窗口。后续排查只保留一个书房实例，设置尺寸后同时核对 `innerWidth/innerHeight` 和实际画布尺寸。没有据此修改 AO、阴影、后期或渲染分辨率。

用户随后明确指出测量期间显示器已关闭，并要求停止测试。此前采样只统计浏览器的场景渲染回调，未验证显示状态、真实呈现节奏或亮屏交互流畅度，因此不能作为稳定 60 FPS 的生产验收依据。此前对“已达到约 60 FPS”的表述撤回。停止继续运行 FPS 测试，所有原始记录仅保留用于排查回溯，亮屏性能验收保持待完成。

## 实施步骤

1. 阅读相关方案，确认引擎限帧逻辑及当前实际浏览器状态。
2. 采集基线，解除限帧并定位剩余成本；根据实测决定是否需要其他优化。
3. 复测六视角、移动与相机切换，检查画面与运行错误。
4. 执行现有测试、类型检查、生产构建；记录结果和适用边界。
5. 同步文档、检查链接和 Git 差异，仅提交本任务文件并推送当前分支。

## 验收方法

- 引擎不存在 30 FPS 上限，前台场景可超过 30 FPS，高刷不会被应用固定在 60。
- 60 Hz 环境下预热后连续采样，目标接近 60 FPS；帧间隔 P95 及超时帧比例用于识别平均 FPS 掩盖的卡顿。
- GPU 计时使用引擎 timer query，查询不可用或 disjoint 时明确标记，不用 CPU 提交时间替代。
- 六个视角、第一人称 WASD、设置开关、切换封闭房间后的阴影正常，未引入运行错误。
- `npm test`、`npm run typecheck` 和生产构建通过；视觉效果如有调整保存可复核证据。

## 实施结果

### 已完成的代码

- 删除 `RoomScene` 中的 `engine.maxFPS = 30`，保留引擎默认无应用限帧的行为；保留隐藏页面暂停、硬件缩放和全部画面参数。
- 新增 [RoomCollisions.ts](../../src/examples/RoomCollisions.ts)，在按材质合并家具前保存原零件的顶点、索引数量，在冻结矩阵后建立对应碰撞分区及局部包围盒。通过 `getCollidingSubMeshCandidates` 提供候选，未登记的建筑和导入模型沿用原回调。
- 碰撞分区共享原几何，不加入渲染子网格、不增加代理网格或绘制批次；继续使用原三角形进行精确碰撞检测，没有关闭碰撞或改为近似包围盒碰撞。该分区仅适用于本项目矩阵已冻结的静态合并家具。
- 临时性能面板和应用接入已从交付源码移除。相关方案的后续交互性能目标统一更新为 60 FPS，已有历史样本原样保留。

### 已完成的检查

- `npm test`：19 项通过。新增检查覆盖直接阻挡、间隙、侧向滑动、越过障碍、较大位移、真实房间中的 18 组第一人称扫掠与原算法结果等价，以及未登记网格的回退行为。
- 局部扫掠的候选三角形检测减少至少 90%；合并网格的顶点、索引、网格数量及单一渲染子网格保持不变。这是算法检查结果，不代表亮屏 FPS 测量。
- `npm run typecheck`、`npm run build -- --mode production`：通过。生产构建仍有既有的资源/入口大小和 runtimeChunk 建议三项警告，资源体积专项继续单独实施。
- `git diff --check` 和文档链接检查在提交前执行。最终生产构建的额外浏览器复核因用户要求停止测试而取消，不再追加测试。
