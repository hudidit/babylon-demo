## 背景与现状

方案建立时书房已完成主要材质、软体家具、硬质细节、接触关系和窗边场景优化。用户希望了解场景需要的磁盘空间，并指出古董柜和书架造型并不复杂，文件却较大。本方案以资源盘点和 GLB 拆解为依据，规划减小交付资源的路径。此后第 7、8 项使用痕迹与镜头后期已独立完成，本轮阶段 A 按该最新场景重建基线。

场景入口为 [app.ts](../../src/app.ts) → [BasicExamples.ts](../../src/components/BasicExamples.ts) → [Room.ts](../../src/examples/Room.ts)。方案建立时书房使用 18 个外部素材文件，场景相关源码为 9 个 TypeScript 文件和 1 个包含内联 CSS 的 HTML；阶段 A 核对素材不变，源码增加至 11 个 TypeScript 文件和 1 个 HTML。其他示例和其素材仍保留在项目中。

## 目标与范围

### 首轮范围

1. 在保留两个模型现有形状、UV、层级与摆放的前提下，降低六张内嵌贴图的交付体积。
2. 建立可复现的资源处理记录、体积统计和仅包含当前书房依赖的发布清单。
3. 提供明确的生产构建流程，保留现有调试功能和动态分包，发布时带齐运行素材。
4. 维持当前画面、书架内物品布局、碰撞、投影、预设视角和第一人称交互。

### 建议预算

下列为首轮预算。阶段 B、C 已验证运行素材及构建加素材的字节数，阶段 D、E 已通过独立发布目录验收；不得为达标接受明显画质损失。原模型预算为 4 MiB，已根据近景证据调整为 4.25 MiB。

| 首轮指标 | 当前基线 | 建议目标 |
| --- | ---: | ---: |
| 两个目标 GLB 合计 | 38.06 MiB | 不超过 4.25 MiB；已实现 4.13 MiB，减少 89.14% |
| 当前书房全部运行素材 | 49.07 MiB | 不超过 16 MiB；实际 15.14 MiB，减少 69.15% |
| 保留调试功能的完整生产交付文件 | 73.26 MiB | 不超过 41 MiB；实际 39.41 MiB，减少 46.21% |

首轮不以 JS 本身继续缩小为前提：沿用约 24.19 MiB 的生产产物，加不超过 16 MiB 的素材，约为 40.19 MiB，预留少量清单等文件空间。若近景必须保留部分 2K 贴图导致预算未达成，应保存对比证据、实际体积和原因，更新预算后再判定验收，不能只记录“优化完成”。

### 后续评估与范围边界

首轮完成后再评估其他贴图、JavaScript 依赖裁剪、KTX2/WebP 以及程序化书架或柜体。它们不是首轮必做项，也没有已验证的缩减幅度。

本方案不包含整体视觉重做，不扩展已完成的真实感方案第 7、8 项范围，不删除其他示例或其素材，不清理用户无关文件，不改写 Git 历史。首轮保留现有调试能力；删除调试发布分包需要单独确定产品范围。压缩后的资源提交不会自动清除 Git 历史中的旧大文件，不能据此承诺本地项目同步缩小相同体积。

## 方案及取舍

### 1. 优先压缩两个 GLB 的贴图

- 以原 GLB 为不可变输入，在临时目录生成候选，保留几何、UV、材质引用和节点变换，避免依赖旧顶点数据的书架布局检测失效。
- 两个模型均先生成最长边 1024 的候选，近景不合格的贴图再单独保留 2048，不要求同一模型的三张图具有相同分辨率。使用 glTF Transform 配合明确配置的图像编码器处理尺寸和编码，记录工具版本与参数；其官方工具支持在模型内调整图片，无需重建几何。[工具说明](https://gltf-transform.dev/modules/functions/functions/textureCompress)
- 颜色贴图可先对质量 85、90、95 进行小范围比较，最终参数由画面和字节数共同确定。法线及粗糙度/金属度作为数据贴图独立选择质量与采样，不直接套用颜色图的压缩档位。
- 首轮优先继续使用现有 JPEG/GLB 加载路径，减少新增解码器和运行依赖；对法线与材质数据检查有损压缩带来的块状噪声、错误高光与表面波纹，必要时提高质量或采用兼容的无损候选。
- 保持颜色贴图的 sRGB 解释及数据贴图的线性解释，保留法线方向约定。两个旧模型使用的是金属度/粗糙度贴图，不假定它们自带独立 AO 通道，也不盲目按项目其他材质的 ARM 格式重打包。
- 筛选候选时检查 UV 边界、木纹、抽屉缝、边缘细节与粗糙度变化。正式采用后同步资源摘要与处理记录，交付目录只保留选定版本。

2026-10-15 阶段 B 实际选择：比较 7 档候选后采用 `detail-c85`，颜色为 2K / JPEG 85、金属度与粗糙度为 1K / JPEG 90、法线为 1K / JPEG 95，均为 4:4:4；法线缩放后重新归一化。全 1K 候选在模型近景中木纹偏软，保留 2K 颜色后两个模型为 4.13 MiB，因此将模型预算由 4 调整为 4.25 MiB；全部素材 16 MiB 和完整交付 41 MiB 的预算不变。

转换工具改用已安装的 Sharp 0.35.5 与专用 GLB 图片重打包脚本：本机没有 glTF Transform，直接重打包可逐字节保留全部非图片 bufferView，并对除容器偏移/长度之外的 JSON 语义做摘要校验。没有新增项目依赖或加载器；节点、UV、几何、材质引用和采样设置保持原件一致。源文件始终从校验过的历史提交读取。

每次编码都从校验过的原件开始，避免把上一次有损结果作为新输入。原件通过上述基线提交保留，不在 `public` 中同时新增一份大文件备份。

### 2. 补齐生产构建与发布资源清单

- 规划增加明确的生产构建命令，保留开发服务流程；生产模式开启压缩等优化，避免将当前默认开发产物用于正式交付。[Webpack 生产构建说明](https://webpack.js.org/guides/production/)
- 从当前 18 个运行素材及 HTML、所有构建分包建立发布白名单，另纳入必要的来源和授权说明。素材保留运行时相对路径，自动复制到最终发布目录；清单必须覆盖动态拼接路径、GLB 外部依赖和未来可能增加的本地解码文件。
- 整个 `public` 超出当前书房依赖的约 147.83 MiB 主要属于其他示例。通过发布白名单排除它们，而非从开发仓库删除；不能把排除其他示例的收益再次计入以 18 个素材为基线的缩减幅度。
- 当前 Inspector 已通过动态 `import()` 按需加载。保留这一行为，不把“增加懒加载”重复算作新成果；完整交付大小仍须包含所有调试及编辑器分包。
- 发布目录应能独立托管，不能依赖开发服务器从 `public` 补齐缺失素材。浏览器验证全部视角和调试入口，确认没有缺失分包或 404。

### 3. 后续按测量结果处理其他资源和 JS

| 方向 | 选择依据 | 取舍及推进条件 |
| --- | --- | --- |
| 亚麻、扶手椅等次级资源 | 实际占用、屏幕覆盖及近景细节 | 大资源完成后再逐项比较；当前沙发不足 1 MiB，优先级较低 |
| 木材贴图复用 | 已有木材图集仅约 0.46 MiB | 适合新建家具或风格统一，不能直接替换旧模型贴图而假定 UV 和磨损分布一致 |
| 窗景与环境贴图 | 窗景已为 1600 × 1165 JPEG，HDR 已为 1K | 先确认视觉收益与节省量，保留窗景透视及 HDR 动态范围，不为减小文件破坏照明 |
| 引擎模块与注册逻辑 | 主 JS 仍约 8.17 MiB | 先分析构建模块和副作用，再处理未使用入口及过宽导入，验证加载器、材质、阴影和调试正常；不能机械替换所有包入口。[Tree Shaking 说明](https://webpack.js.org/guides/tree-shaking/) |
| 调试工具的发布范围 | 全部分包约占 16.02 MiB，包含调试等功能 | 如后续另需无调试的浏览版本，独立定义构建配置与能力差异，并分别统计；首轮不删除 |
| KTX2 或 WebP 等格式 | 第一轮结果仍超预算，或有明确显存/加载需求 | 做单资源试验并核实加载兼容性、扩展声明、颜色空间及本地解码依赖；新增文件计入总预算 |
| 几何压缩 | 两个模型非贴图部分合计仅约 0.47 MiB | 首轮收益有限，不优先引入 Draco/Meshopt 解码器；后续按净节省量评估 |

代码分包主要改变请求时机，单纯拆分文件不能等同于减小磁盘体积。HTTP gzip/Brotli 统计为传输指标；若同时发布原文件和预压缩副本，需把副本加入磁盘总量，不能用压缩后的下载量替代交付目录体积。

### 4. 程序化书架和古董柜作为备选

程序建模适合需要可调尺寸、隔层与统一木材的家具。书架可由板材、背板、装饰条和倒角生成；古董柜可由柜体、抽屉、柜脚与把手生成，优先复用现有木材和黄铜材质。

该路径的收益来自共享材质和减少专用贴图，重写几何本身只有很小的磁盘收益。完全保持原有木纹、磨损及局部表面细节仍需额外制作，且程序网格必须控制合并与绘制成本，不能假定代码生成就更快。

若后续选择这一路径，应单独更新本方案范围或新建实现方案，至少处理：

1. 保持外包尺寸、落地、摆放、倒角与场景风格；将网格按材质合并，保留碰撞和投影。
2. 书架现有 [BookshelfLayout.ts](../../src/examples/BookshelfLayout.ts) 及 [布局测试](../../tests/room-layout.test.cjs) 读取实际模型隔层，并验证六个隔层、书本和花瓶的贴合；重建时需要明确提供新的隔层数据或适配测量接口，不能直接删掉旧模型而保留原假设。
3. 保存专门的近景对比，确认是否接受木纹及磨损风格变化，再移除对应运行素材。

## 验收方法

### 文件体积与可复现性

- 对明确的资源清单按原始字节求和，同时报告两个 GLB、全部运行素材、完整生产产物及最终发布目录；文件系统分配空间作为另列指标。
- 首轮按调整后的 4.25 MiB / 16 MiB / 41 MiB 预算核对；模型预算由原 4 MiB 调整，依据见阶段 B、C 近景和候选记录。
- 对比转换前后的模型几何数据、节点变换、UV、包围盒和材质关联；首轮仅替换图片及必要的封装信息。
- 发布目录不夹带原件备份、候选、测试截图、开发依赖或其他示例素材；必要的来源/授权说明计入实际发布目录。
- 相同输入、工具版本及参数可重新生成同等结果；摘要变化需能追溯到工具版本或处理参数变化。

### 画面与交互

- 同机、相同视口及渲染尺寸下比较全景、阅读区、书桌、藏书角和第一人称，增加古董柜与书架的局部近景，并检查第一人称可接近的观察距离。
- 木纹、抽屉缝、隔板与边缘细节可辨识；没有新增明显模糊、块状噪声、材质色偏、错误金属反光、法线方向错误或 UV 接缝。
- 书架六个隔层及书本、花瓶的尺寸与位置正常；家具落地、碰撞、阴影和第一人称移动保持当前行为。
- 在独立托管的生产页面上检查素材、动态分包及调试入口，浏览器无新增运行错误或 404；不以开发服务器能打开代替发布验收。

### 工程检查与性能

- 资源或构建接入后执行 `npm test`、`npm run typecheck`、`npm run build`，并执行最终确定的生产构建命令。现有几何测试不会验证贴图画质，不能代替浏览器对比。
- 如新增资源清单或转换脚本，仅增加能验证实际风险的检查，例如资源缺失、摘要、尺寸上限、发布依赖完整性及模型结构保持。
- 原定的帧率/CPU 采样已按用户要求停止，本方案不再将性能采样作为体积优化完成条件。后续在相同设备和渲染条件下的性能验收按 [帧率修复方案](2026-10-15-room-frame-rate.md) 的稳定 60 FPS 目标验收；不能因文件变小就推断帧率必然提高。阶段 A 的约 30 FPS 数据保留为当时应用限帧条件下的原始基线。
- 若比较加载表现，使用禁用缓存的相同浏览器条件，记录实际请求量、传输字节和场景可用时间；网络条件和解码成本单独记录，不承诺未经验证的加载加速倍数。

## 风险与回滚

| 风险 | 应对 |
| --- | --- |
| 1K 候选在第一人称近景过软 | 按贴图和可见细节保留必要的 2K，提高质量；保存预算调整依据 |
| 数据贴图压缩造成异常反光或法线伪影 | 保持线性与通道约定，逐类比较编码，失败时保留更高质量候选 |
| 资源重打包破坏层级或书架测量 | 首轮不优化几何，检查节点、UV 和包围盒，运行实际模型布局测试 |
| 新格式引入额外解码和兼容问题 | 首轮沿用现有加载路径；新格式单独试验并计算解码器净成本 |
| 发布白名单遗漏动态依赖 | 对最终目录独立托管验证所有视角与调试功能，保留完整依赖清单 |
| 文件变小但本地仓库占用变化不大 | 分开报告运行资源与开发/Git 空间；本轮不进行历史清理 |

原 GLB 可从本方案基线提交恢复。实现时让贴图替换、构建配置等阶段各自具有清晰提交边界，失败时按阶段恢复；不得通过强制推送或历史改写完成回滚。
